## §1 三方架构对比（wstunnel / pingora / rathole → duotunnel）

### 1.1 运行时模型

| 项目 | 运行时策略 | 关键设计 |
|---|---|---|
| wstunnel | 单个 `tokio::runtime::Builder::new_multi_thread()` + JoinSet 任务追踪 | `Weak<Mutex<JoinSet>>` 避免强引用循环；Drop 时 `abort_all` |
| pingora | `NoStealRuntime`：N 个独立单线程 tokio Runtime 组成线程池 | 彻底无 work-steal，连接 pin 在固定线程，CPU cache 亲和性极好 |
| rathole | `tokio::runtime::Builder::new_multi_thread()` 标准模式 | 无运行时抽象，简单直接 |
| duotunnel | 多线程标准模式 + `TOKIO_WORKER_THREADS` 环境变量覆盖 | 无法切换 no-steal 模式；无 JoinSet 任务生命周期追踪（此后由 TODO-96 补上，见 §2） |

Pingora 核心洞察：work-steal 调度在高并发转发场景下的 task 迁移会造成 CPU L1/L2 cache line 失效；`NoStealRuntime` 让每条连接的热数据固定在一个核心上。

### 1.2 I/O Copy 引擎与缓冲区策略

| 项目 | 设计 |
|---|---|
| wstunnel | `read_buf` 直写 writer 自带的 `BytesMut`，零中间拷贝。**依赖 writer 自控内部缓冲**（自定义 WS/HTTP2 writer） |
| pingora | `hot_queue: ArrayQueue<N=16>` 无锁热队列 + `Mutex<HashMap>` 冷路径兜底（LRU 淘汰） |
| duotunnel（当时） | `SegQueue<Vec<u8>>` 全局池；`SegQueue::len()` 是 $O(N)$ 遍历，且每次归还都调用；`resize(buffer_size, 0)` 零化后又被 `reader.read()` 立即覆盖 |

**wstunnel 的 `read_buf` 直写模式在 duotunnel 上不可行**：quinn `SendStream` 只提供 `write_all(&[u8])`，不暴露内部帧缓冲，强行移植需要 fork quinn 或使用 unsafe transmute，风险高、收益存疑。该方向已列入「确认不做」（§3）。

### 1.3 连接池架构

| 项目 | 设计 |
|---|---|
| wstunnel | `bb8` 管理 HTTP/WS 上游连接，`has_broken` 用 `Option<Stream>=None` 表示已消耗 |
| pingora | `DashMap<GroupKey, Pool>` 外层分桶 + 每桶 16-slot `ArrayQueue` 热队列 + `Lru` 全局淘汰 |
| rathole | 控制通道建立后预创建 N 个（默认 8）数据通道并缓冲，消除访客到达时的握手延迟 |
| duotunnel（当时） | Egress 侧每次全新建立 TCP 连接到上游，无复用 |

### 1.4 热重载与 TLS 证书动态更新

| 项目 | 设计 |
|---|---|
| wstunnel | `notify::recommended_watcher` 监听证书文件 + `AtomicBool` 标志位，建连前检查并重建 acceptor；文件删除后用独立线程轮询重建，不占用 async runtime |
| rathole | TOML diff 驱动的增量热重载（`Add`/`Delete` service 级事件） |
| duotunnel | `ArcSwap<RoutingSnapshot>` 整体快照替换，比 rathole 增量 diff 更"暴力"但无局部状态不一致风险；**没有 TLS 证书文件 watch**，证书轮换需重启进程 |

### 1.5 负载均衡算法

| 项目 | 算法 |
|---|---|
| wstunnel | 轮询（bb8 池内 FIFO），无显式 LB |
| pingora | LRU 连接池 + per-key DashMap 分桶，同 key 复用不同 key 隔离 |
| rathole | FIFO channel 分发 |
| duotunnel | **P2C (Power of Two Choices) + 最小 inflight**：小列表 $O(N)$ 扫描，大列表随机采 2 个比较 inflight；`CachePadded<InflightSlot>` 避免 false sharing，thread-local `ROTATING_INDEX` 防止扫描热点。三方中最优 |

### 1.6 DNS 缓存

当时 `EgressDnsCache` 用全局 `tokio::sync::Mutex<()>` 序列化所有域名解析，且每次写入 `(**cache.load()).clone()` 全量复制 `HashMap`。详见 §2 表格 TODO-104。

### 1.7 协议嗅探超时保护（Slowloris）

`SniffRuntime::sniff` 只限制 `max_read_rounds` 和 `max_sniff_bytes`，无绝对时间超时；攻击者可用 1 字节/秒发送数据长期挂起 accept worker。详见 §2 表格 TODO-CR-AUDIT-18。

### 1.8 TLS 实现

| 项目 | TLS 实现 | 密码学后端 |
|---|---|---|
| wstunnel | tokio-rustls + aws-lc-rs（默认）/ ring | aws-lc-rs |
| pingora | rustls + aws-lc-rs / openssl-boringssl | 多后端可选 |
| rathole | native-tls / rustls | ring |
| duotunnel | tokio-rustls + **aws-lc-rs** ✅ | quinn `rustls-aws-lc-rs`，与 wstunnel/pingora 一致 |

### 1.9 过载保护

| 项目 | 机制 |
|---|---|
| wstunnel | bb8 池大小限制 + `connection_min_idle`，池满新请求阻塞 |
| pingora | 无显式过载保护，依赖 OS backlog |
| rathole | `CHAN_SIZE=2048` channel 容量限制 |
| duotunnel | `OverloadLimits` + `maybe_slow_path`，yield/sleep 双阈值 + P2C 选连接——三方中**最精细** |

### 1.10 三方精华特性汇总（当时评估）

| 特性 | 来源 | 当时是否已采纳 |
|---|---|---|
| `read_buf` 零中间拷贝写帧 | wstunnel | ❌ 不可行（quinn `SendStream` 不暴露内部缓冲）|
| `ArrayQueue` 热路径无锁池 | pingora | ❌（用了 SegQueue）→ 见 §2 TODO-CR-AUDIT-16 |
| DashMap + LRU 连接池 | pingora | ❌（无 Egress 池）→ 见 §2 TODO-74 |
| AtomicBool TLS 热重载 | wstunnel | ❌ → 见 §2 TODO-99 |
| P2C 最小 inflight LB | duotunnel | ✅ 已超越三方 |
| Jitter 指数退避 / ArcSwap 热重载 / CachePadded InflightSlot / ConstantTime Token 比较 | duotunnel | ✅ 已超越三方，保持不变 |

## §3 确认不做 / 已放弃清单

| 方案 | 结论 | 原因 |
|---|---|---|
| wstunnel `read_buf` 零拷贝直写帧缓冲 | ⚠️ 不移植 | `quinn::SendStream` 不暴露内部 `BytesMut`，强行移植需 fork quinn 或 unsafe transmute，风险高收益存疑 |
| Pingora `NoStealRuntime` / thread-per-core | ❌ 不推进 | 丢失 Tokio work-stealing，Quinn/Hyper 生态改造成本高，不适合 N:M 汇聚隧道流量；仅在压测证实单 endpoint 打满单核时才重新研究（需 CID-aware eBPF） |
| 两级 L4 upstream 连接池（server/client 双层） | ❌ 已舍弃（TODO-35） | 随 raw TCP 空闲连接池方向一起放弃；HTTP/H2 复用交给 Hyper 协议感知池已足够 |
| rathole 增量 service diff 热重载 | 暂不需要 | duotunnel 场景下 `ArcSwap` 全量快照替换已经零停机且更安全，增量 diff 收益不明显 |
| rathole 预连接数据通道池（提前建好 N 个数据通道等访客） | 未采纳 | QUIC `open_bi()` 的建流成本远低于 TCP 三次握手，不存在 rathole 要规避的"访客到达才建连"的 RTT 惩罚；早期截断需求已由 TODO-76 满足 |
| CPU 绑核（`core_affinity`） | 可选后续 | 依赖 NoSteal 完成后才有意义，而 NoSteal 本身已不推进；macOS 支持也有限 |
